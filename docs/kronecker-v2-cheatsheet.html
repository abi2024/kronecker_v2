Root cause

The window is measured in bytes. Meaning is measured in characters.

UTF-8 charges different scripts different rates. A window that is generous in one language is cramped in another, and nothing in the embedding's parameter count reveals this.

क्ष looks like one character. Unicode stores it as three codepoints — क + halant + ष — at 3 bytes each. Nine bytes for one visual symbol. Three of those and a 32-byte budget is gone.

The part people get wrong

Why more training cannot fix a collision

Dense table

Gradient moves A's row and leaves B's alone. They can separate because they own different parameters.

Kronecker

There is no per-token parameter. One shared matrix receives the same input vector from both. Whatever it does to one, it does to the other.

A fingerprint door with two people who share a print. Improving the scanner never helps — the information isn't there.

Zero at 32 is not a null result. The tokenizer's own audit reports tokens > 32 bytes: 0 — it was built to satisfy the window. The constraint didn't vanish; it was paid for upstream, in the vocabulary.

Who pays, at pos_dim = 16

Latin loses 18 of 108,185 tokens — 0.02%. Devanagari loses 6.3% of its own. Two orders of magnitude of asymmetry from one shared window.

Second mechanism, independent of the window. token_id_to_bytes resolves ids via tokenizer.decode(), which renders every partial-codepoint token as U+FFFD. 1,151 tokens still collide at pos_dim = 32, where truncation contributes nothing. That's the byte-extraction path, not the codec.
The fix

Stop asking "which slot?" Start asking "how much rotation?"

One-hot · a grid
  • Position is an index into a fixed number of columns.
  • Byte 33 has nowhere to go. It is dropped, silently.
  • Longer vocabulary → same cost. Longer token → data loss.
Wave · a circle
  • Each byte value gets a fixed random angle.
  • Position p multiplies that angle — zp. p is a multiplier, not an index.
  • Bind = add angles. Bundle = add arrows. Nothing to fall off.

Why the rotation is load-bearing

Drop it and just add a vector per character: dog and god produce identical codes, because addition ignores order. Every anagram collides. Position-as-rotation is what breaks the tie — and it is exactly the binding operation from Holographic Reduced Representations, which is why Plate belongs in your related work.

Why 0.79, not 0.00

कार्य and कार्यक्रम should be near each other — shared prefix, related morphology. That orthographic locality is why Kronecker beat BPE in the first place. A codec that pushed them to zero would destroy the thing worth keeping. Near but distinguishable is the target.

Parameter parity, by construction

one-hot: 256 × 16 = 4096 real  ·  wave: 2048 complex × 2 = 4096 real

Same input width → same Linear(4096, d_model) → same trainable parameter count. Any difference you later measure cannot be explained by "the new one was bigger." This is asserted by test_equal_params.py, not by a sentence in a README.

Three things that look like test failures and are actually facts about your codec

Reproducibility

torch.rand isn't portable

PyTorch guarantees CPU RNG reproducibility within one platform and build. Windows and Linux vectorize differently — two "seed 0" codecs, different numbers.

→ numpy PCG64: integer arithmetic, same stream everywhere

cos and sin aren't either

MSVC's libm and glibc's differ in the last bits. The wave codes cannot be pinned bitwise across operating systems by any amount of seeding.

→ pin phases exactly (no trig), pin codes by value at 1e-4

A matmul isn't row-order stable

Identical input rows at different batch positions can give bitwise-different output — BLAS tiles and schedules the reduction differently.

→ exact on the lookup, allclose on the projection

Why it matters: develop on Windows, train on a rented Linux box, and without these fixes your trained model uses a different codec than the one you audited — and every number in the paper describes the wrong object. Silently.
